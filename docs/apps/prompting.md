# 提示词编写指南

App 的好坏，八成取决于提示词。这篇讲**怎么分工、怎么写格式契约、怎么迭代**，
不涉及任何代码。

---

## 1. 五个文件的分工

应用目录里的提示词不是随便堆的，每个文件有固定位置和用途：

| 文件 | 拼到哪里 | 该写什么 | 不该写什么 |
|---|---|---|---|
| `role.txt` | 系统提示**最前** | 你是谁、怎么说话、自称 | 剧情、规则细节 |
| `charaset.txt` | 系统提示中部（设定段） | 世界观、人物关系、背景 | 输出格式 |
| `rules.txt` | 系统提示**最后** | **输出格式**、硬性规则、枚举值 | 大段世界观（它会挤掉格式约束的注意力） |
| `summary.txt` | 只在**压缩历史**时单独发给模型 | 让模型"把这段对话压成摘要"的指令 | 角色的台词、剧情 |
| `prelogue.txt` | 开局展示给玩家 | 开场白/第一幕 | 规则 |

> 放错位置的典型后果：把格式要求写在 `charaset.txt` 里 → 因为它是中间段、被后面的
> `rules.txt` 冲淡，模型经常忘记按格式输出。

## 2. 格式契约：程序真的会"读"你的输出

除了 `custom` 智能体，**所有内置类型都会按标记逐行解析 AI 输出**。
也就是说：标记不只是"给玩家看的排版"，它是程序和你之间的**接口**。

一条铁律：**标记必须独占一行，且前后不要加修饰**。

```text
正确 ✅                      错误 ❌
==对话==                     **==对话==**
台词                         ```
（动作）                     ==对话==
                             ```
```

常见的翻车写法：

| 写法 | 为什么坏 |
|---|---|
| `==对话== 台词` 写在同一行 | 程序按"行首前缀"匹配标记，同一行会整行被当正文 |
| 用 `### 对话`、`[对话]` 代替 | 标记名写错 = 永远匹配不上，格式段被当普通文字显示 |
| 标记外面套代码块 | ` ``` ` 会被当成正文，后续解析全乱 |
| 在标记行加粗/加空格缩进 | 行首多一个空格就匹配失败 |

**每种类型的标记是固定的**（改标记等于改程序），清单见 [builtin-apps.md](builtin-apps.md)。
你能改的是标记**里面的内容和枚举值**。

---

## 3. 枚举值：写死，并且两处一致

带 `键=值` 的段（如 `==场景==`、`==角色==`）是喂给程序的选图/状态数据，所以值必须是**有限集合**：

```text
==场景==
地点=客栈          ← 只能从你声明的枚举里挑
时间=夜晚
表情=冷漠
位置=前
```

要做两件事：

1. 在 `rules.txt` 里把枚举写死，给模型看到候选：

   ```
   地点只能是：客栈|山道|城镇|密室（不得自创）
   ```

2. 如果目录里有 `validator.json`，把同样的枚举写进去（它是白名单，不在名单里的键值会被**静默丢弃**）：

   ```json
   { "rules": [
     { "keyPattern": "地点", "valuePatterns": ["客栈", "山道", "城镇", "密室"] }
   ] }
   ```

**两处不一致是最常见的坑**：`rules.txt` 里加了新地点，忘了改 `validator.json`
→ 模型输出的新地点被丢掉 → 背景不换、立绘不换，但日志里一句错误都没有。

> 懒得维护就先删掉 `validator.json`：不校验 = 全部接受。等格式稳定再加回来。

## 4. 人设不崩的四个技巧

模型"崩人设"通常不是模型笨，是提示词没给够约束。

**① 用"禁止清单"代替"希望"**

```
❌ 请尽量保持古代人的说话方式
✅ 禁止使用：现代词汇（如"系统""数据""OK"）、网络用语、表情符号、英文单词
```

**② 给语气示例（2~3 条足够）**

```
示例：
用户：今天天气不错。
角色：「是啊。」他抬眼看了看檐下的雨，「可惜这样的天，总不会太久。」
```

示例比形容词有效十倍——但它也容易让模型**照抄**，所以给 2~3 条、换不同场景。

**③ 把"不要说"写成可执行的规则**

```
❌ 不要出戏
✅ 永远不要提及"AI""模型""提示词"，也不要描述自己在扮演角色
```

**④ 给一个"跑偏后怎么回来"的兜底**

```
用户问与剧情无关的问题时，用「此事与你我无关」带过，然后继续推进当前场景。
```

## 5. 节奏与长度

| 想控制 | 写法 |
|---|---|
| 回复太长 | `每轮正文不超过 200 字` |
| 回复太短 | `每轮至少 3 段，其中至少 1 段是环境描写` |
| 推进太慢 | `每轮剧情必须发生一个新变化（新人物/新冲突/新线索）` |
| 推进太快 | `不要在一轮内结束当前场景，至少保留 3 轮` |
| 选项数量 | `给出 3~5 个编号选项，最后一行固定为"选择你的行动。"` |

字数要求要**具体到数字**，"简短一些"这种描述模型会忽略。

## 6. 摘要提示词（`summary.txt`）怎么写

这个文件**玩家永远看不到**，它是"给模型的一次性指令"，用来把越来越长的对话压成摘要。

写法要点：

1. 明确输入结构：告诉它你会给「前情提要 + 新的对话块」；
2. 明确输出结构：**只输出摘要**，不要复述对话、不要加解释；
3. 给分节标题，便于程序按节合并：

   ```
   请把输入压缩成以下六节，只输出这六节，不要任何额外说明：
   ==永久记忆==
   ==故事脉络==
   ==约定==
   ==角色状态==
   ==持有物品==
   ==前情提要==
   ```

4. 给长度约束（如"前情提要约 1000 字，其余各节不超过 200 字"）；
5. 禁止嵌套标记：`各节内部不得再出现 == 符号`。

> 一个 `summary.txt` 可以给多个角色共用（角色设定不参与摘要），
> 但世界观的差异较大时，建议分开写，并在摘要指令里点明"这是哪个故事"。

## 7. 迭代方法（很重要）

**改提示词 → 重启 → 开新对话 → 看输出**。四步，别跳。

1. **必须重启**：提示词是在服务启动时一次读进内存的，改完不重启不生效（`custom` 智能体例外，它是即时生效的）。
2. **必须开新对话**：旧对话里带着旧提示词生成的上下文，模型会"学着"旧的格式继续错。
   用一个新 `chatid` 验证才干净。
3. **看原始输出**：界面会把格式段隐藏起来，想确认到底写了什么，
   就看存档文件 `save/saveData/<chatid>.json`（明文 JSON），里面存的是模型原文。
4. **一次只改一处**：同时改 3 个文件，出问题就不知道是哪个导致的。

验证顺序建议：

```
先验证格式 → 再验证人设 → 最后调剧情节奏
（格式不对，后面都是白调，因为程序会不断要求重写，浪费额度）
```

## 8. 各类型的格式契约速查

| 类型 | 程序会解析的标记 | 你能改的 |
|---|---|---|
| `talk` | `==对话==`、`==场景==`（键值） | 台词风格、场景键的枚举值 |
| `trpg` | `==场景==`、`==对话==`、`==角色==` | 同上 + 多角色表情/站位 |
| `galgame` | `你选择：`、`==情景剧本==`、`==操作==` | 剧情风格、选项内容 |
| `wuxia` | `你选择：`、`==故事大纲==`、`==情景剧本==`、`==属性面板==`、`==操作==` | 属性项、大纲要求 |
| `write` | `==大纲==`、`==内容==` | 文风、字数、章节结构 |
| `sql` | 无（标记与代码判据不一致，见 builtin-apps） | 输出习惯 |
| `custom` | **无**，完全看你写的核心规则 | 全部 |
| `group` | 无标记，纯文本 | 语气、长度（群聊要短） |

> `custom` 最自由、也最容易格式失控——因为它没有任何解析器帮你兜底。
> 想要稳定的结构化输出，选一个有对应类型的 app 更省力。

## 9. 提示词检查清单

上线前逐条确认：

- [ ] 标记独占一行，前后无加粗、无缩进、无代码块
- [ ] 标记名与 [builtin-apps.md](builtin-apps.md) 里该类型的清单完全一致
- [ ] `rules.txt` 里的枚举值 = `validator.json` 里的白名单
- [ ] 文件是 UTF-8 **无 BOM**（带 BOM 会把乱码塞进提示词开头）
- [ ] 禁止清单用"禁止…"，而不是"请尽量…"
- [ ] 有 2~3 条语气示例
- [ ] 字数/选项数量写成了具体数字
- [ ] `summary.txt` 只输出摘要、不含台词
- [ ] 改完重启过，并且是用**新对话**验证的
